## 2. Задача и сохранённая модель

В сельской библиотеке каждая книга есть в одном экземпляре. Читатели приходят по расписанию, выбирают от одной до трёх книг и возвращают полученные книги через заданное число дней. На недоступные книги создаются заявки. После возврата библиотекарь уведомляет ожидающих и резервирует книгу одному из них.

Предметная модель, формат входных данных, стратегии FIFO/LIFO, `request_rule`, config, CLI, логирование и статистика сохранены из предыдущих ИДЗ. Основное изменение ИДЗ №3 - переход от взаимодействующих pthread к взаимодействующим процессам.

**Входные параметры:** книги, читатели, дни посещений, желаемые книги, срок чтения, стратегия выбора заявки (`strategy`) и правило формирования заявок (`request_rule`). Период моделирования задаётся через `total_days` или `-d`; по умолчанию 13 дней.

**Основные инварианты:**

- У экземпляра книги не более одного владельца.
- Читатель не получает ту же книгу повторно до возврата.
- Выданная книга отсутствует в доступном фонде.
- Возвращённая книга свободна или зарезервирована одному ожидающему.
- Закрытая заявка не обслуживается повторно.

Внутренние контракты функций и основные инварианты дополнительно проверяются через `SOFT_ASSERT`.

## 3. Процессы

Программа написана на C11 для Linux с использованием libc, системных вызовов и POSIX IPC.

Один родительский процесс управляет моделированием и условными днями. `Librarian` работает в отдельном дочернем процессе, поскольку самостоятельно обрабатывает возвраты, уведомления и резервирование. Каждый `Reader` также является отдельным процессом, так как имеет собственное расписание и поведение.

`Book` и `Request` процессами не являются: это общие данные без самостоятельного поведения.

### Модельный день

Родительский процесс изменяет общий `current_day` и задаёт порядок фаз.

1. Родитель разрешает библиотекарю выполнить возвраты.
2. Библиотекарь обрабатывает возвраты, уведомления и резервирование и сообщает о завершении.
3. Родитель разрешает работу читателям.
4. Каждый читатель проверяет расписание и при необходимости выполняет посещение.
5. Родитель ждёт завершения всех читателей и только после этого переходит к следующему дню.

Возвраты выполняются до посещений, поэтому сохраняется логика предыдущей версии программы.

Для общего состояния используется POSIX shared memory. Между процессами передаются индексы и идентификаторы, а не указатели на локальную память процессов.

### Реализованные варианты

| Версия | Создание процессов | Общее состояние | Синхронизация |
| --- | --- | --- | --- |
| 4-5 баллов | родитель создаёт дочерние процессы через `fork()` | POSIX shared memory | неименованные POSIX-семафоры |
| 6 баллов | родитель создаёт дочерние процессы через `fork()` | POSIX shared memory | именованные POSIX-семафоры |

Предметная логика и способ хранения общего состояния в обеих версиях совпадают. Основное различие - способ межпроцессной синхронизации.

## 4. Реализация на 4-5 баллов

Родительский процесс создаёт через `fork()` один процесс `Librarian` и отдельный процесс для каждого `Reader`.

Общее состояние библиотеки создаётся через `shm_open`, `ftruncate` и `mmap`.

Для синхронизации используются неименованные POSIX-семафоры, размещённые в shared memory и созданные с `pshared = 1`.

Отдельные семафоры используются для запуска библиотекаря, запуска читателей и передачи родителю информации о завершении фаз. Ещё один семафор с начальным значением `1` защищает общее состояние библиотеки.

Проверка доступности книги и изменение её владельца или резерва выполняются внутри одной критической секции, поэтому два процесса не могут одновременно выдать один экземпляр книги.

После завершения родитель собирает дочерние процессы через `waitpid()`, уничтожает семафоры, освобождает отображение общей памяти и удаляет объект shared memory.

## 5. Реализация на 6 баллов

Вторая программа сохраняет ту же схему процессов, порядок модельного дня и POSIX shared memory.

Основное изменение - использование именованных POSIX-семафоров вместо неименованных.

Семафоры создаются через `sem_open()`. Для каждого запуска используются уникальные имена, содержащие UID и PID родительского процесса, поэтому разные запуски программы не используют одни и те же объекты синхронизации.

Как и в предыдущей реализации, отдельные семафоры отвечают за защиту общего состояния, запуск библиотекаря, запуск каждого читателя и завершение фаз.

После окончания работы открытые семафоры закрываются через `sem_close()` и удаляются через `sem_unlink()`. Shared memory освобождается и удаляется отдельно.

Таким образом, версия на 6 баллов сохраняет поведение программы на 4-5 баллов, но реализует второй требуемый способ межпроцессной синхронизации.

## 6. Завершение

После последнего дня родитель устанавливает общий признак завершения и будит процессы, которые могут ожидать на семафорах. Дочерние процессы проверяют этот признак и выходят, после чего родитель собирает их через `waitpid()`.

SIGINT (`Ctrl+C`) и SIGTERM обрабатываются через `sigaction`. Обработчик только устанавливает флаг `volatile sig_atomic_t stop_requested`. Вывод, ожидание процессов и освобождение ресурсов выполняются обычным кодом программы.

В версии 4-5 при завершении уничтожаются неименованные семафоры и shared memory. В версии 6 закрываются и удаляются именованные семафоры, после чего также удаляется shared memory.

При частичном создании ресурсов освобождаются только успешно созданные объекты.

## 7. Сборка и запуск

Нужны Linux, CMake и компилятор C11 с поддержкой POSIX shared memory и семафоров.

Сборка:

```bash
cmake -S . -B build
cmake --build build
```

Версия на 4-5 баллов:

```bash
./run4_5.sh
```

Версия на 6 баллов:

```bash
./run6.sh
```

Скрипты по умолчанию загружают `config.txt` из корня проекта. При прямом запуске `./build/library_4_5` или `./build/library_6` без `-c` используются встроенные данные.

Можно передавать те же параметры, что и в предыдущем ИДЗ:

```bash
./run4_5.sh -c config.txt -d 20 -r 5
./run6.sh -c config.txt -d 20 -r 5
```

Опции: `-d / --days` - количество дней, `-r / --reading-days` - срок чтения, `-c / --config` - файл конфигурации, `-h / --help` - справка. Значения CLI имеют приоритет над config.

## 8. Дополнительные возможности

- **Комментарии и Doxygen.** Логические блоки поясняются обычными комментариями, публичные структуры и функции описаны Doxygen-комментариями.
- **clang-format.** Исходные `.c` и `.h` приводятся к единому стилю через `.clang-format`.
- **SOFT_ASSERT.** Внутренние контракты и инварианты проверяются отдельно от пользовательских ошибок.
- **Работа с файловыми дескрипторами.** Логирование использует `open`, `write`, `close`.
- **Логирование.** Основные события и итоговая статистика сохраняются в `library.log`.
- **Статистика.** В конце выводятся количество посещений, выдач, возвратов, созданных и выполненных заявок, уведомлений.
- **Config и CLI.** Параметры модели можно изменять через config-файл и аргументы командной строки.
- **Обработка сигналов.** SIGINT и SIGTERM приводят к корректному завершению дочерних процессов и освобождению IPC-ресурсов.
- **Тестовые сценарии.** Для каждой реализации предусмотрен отдельный интеграционный скрипт.
