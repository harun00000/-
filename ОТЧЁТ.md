## 2. Задача и сохранённая модель

В сельской библиотеке каждая книга есть в одном экземпляре. Читатели приходят по расписанию, выбирают от одной до трёх книг и возвращают полученные книги через заданное число дней. На недоступные книги создаются заявки. После возврата библиотекарь уведомляет ожидающих и резервирует книгу одному из них.

Предметная модель, формат входных данных, стратегии FIFO/LIFO, `request_rule`, config, CLI, логирование и статистика сохранены из предыдущих ИДЗ. Основное изменение ИДЗ №3 - переход от взаимодействующих pthread к взаимодействующим процессам.

**Входные параметры:** книги, читатели, дни посещений, желаемые книги, срок чтения, стратегия выбора заявки (`strategy`) и правило формирования заявок (`request_rule`). Период моделирования задаётся через `total_days` или `-d`; по умолчанию 13 дней.

**Основные инварианты:**

- У экземпляра книги не более одного владельца.
- Читатель не получает ту же книгу повторно до возврата.
- Выданная книга отсутствует в доступном фонде.
- Возвращённая книга свободна или зарезервирована одному ожидающему.
- Закрытая заявка не обслуживается повторно.

Внутренние контракты функций и основные инварианты дополнительно проверяются через `SOFT_ASSERT`.

## 3. Процессы

Программа написана на C11 для Linux с использованием libc, системных вызовов и POSIX IPC.

В версиях 4-5 и 6 один родительский процесс управляет моделированием и условными днями. `Librarian` работает в отдельном дочернем процессе, поскольку самостоятельно обрабатывает возвраты, уведомления и резервирование. Каждый `Reader` также является отдельным процессом, так как имеет собственное расписание и поведение.

В версии 7-8 те же роли выполняют независимые программы Coordinator, Librarian и Reader.

`Book` и `Request` процессами не являются: это общие данные без самостоятельного поведения.

### Модельный день

Управляющий процесс (родитель или Coordinator) изменяет общий `current_day` и задаёт порядок фаз.

1. Управляющий процесс разрешает библиотекарю выполнить возвраты.
2. Библиотекарь обрабатывает возвраты, уведомления и резервирование и сообщает о завершении.
3. Управляющий процесс разрешает работу читателям.
4. Каждый читатель проверяет расписание и при необходимости выполняет посещение.
5. Управляющий процесс ждёт завершения всех читателей и только после этого переходит к следующему дню.

Возвраты выполняются до посещений, поэтому сохраняется логика предыдущей версии программы.

В версиях 4-8 для общего состояния используется POSIX shared memory. Между процессами передаются индексы и идентификаторы, а не указатели на локальную память процессов.

### Реализованные варианты

| Версия | Создание процессов | Общее состояние | Синхронизация |
| --- | --- | --- | --- |
| 4-5 баллов | родитель создаёт дочерние процессы через `fork()` | POSIX shared memory | неименованные POSIX-семафоры |
| 6 баллов | родитель создаёт дочерние процессы через `fork()` | POSIX shared memory | именованные POSIX-семафоры |
| 7-8 баллов | отдельные программы-процессы запускаются независимо | POSIX shared memory | именованные POSIX-семафоры |
| Выше 8 | независимые программы-процессы | POSIX message queues | именованные POSIX-семафоры |

Предметная логика во всех версиях сохранена. Версии 4-8 используют shared memory; в финальной версии единственный экземпляр состояния хранится локально у Coordinator, а обмен выполняется через очереди сообщений.

## 4. Реализация на 4-5 баллов

Родительский процесс создаёт через `fork()` один процесс `Librarian` и отдельный процесс для каждого `Reader`.

Общее состояние библиотеки создаётся через `shm_open`, `ftruncate` и `mmap`.

Для синхронизации используются неименованные POSIX-семафоры, размещённые в shared memory и созданные с `pshared = 1`.

Отдельные семафоры используются для запуска библиотекаря, запуска читателей и передачи родителю информации о завершении фаз. Ещё один семафор с начальным значением `1` защищает общее состояние библиотеки.

Проверка доступности книги и изменение её владельца или резерва выполняются внутри одной критической секции, поэтому два процесса не могут одновременно выдать один экземпляр книги.

После завершения родитель собирает дочерние процессы через `waitpid()`, уничтожает семафоры, освобождает отображение общей памяти и удаляет объект shared memory.

## 5. Реализация на 6 баллов

Вторая программа сохраняет ту же схему процессов, порядок модельного дня и POSIX shared memory.

Основное изменение - использование именованных POSIX-семафоров вместо неименованных.

Семафоры создаются через `sem_open()`. Для каждого запуска используются уникальные имена, содержащие UID и PID родительского процесса, поэтому разные запуски программы не используют одни и те же объекты синхронизации.

Как и в предыдущей реализации, отдельные семафоры отвечают за защиту общего состояния, запуск библиотекаря, запуск каждого читателя и завершение фаз.

После окончания работы открытые семафоры закрываются через `sem_close()` и удаляются через `sem_unlink()`. Shared memory освобождается и удаляется отдельно.

Таким образом, версия на 6 баллов сохраняет поведение программы на 4-5 баллов, но реализует второй требуемый способ межпроцессной синхронизации.

## 6. Реализация на 7-8 баллов

Добавлены отдельные программы `library_7_8_coordinator`, `library_7_8_librarian` и `library_7_8_reader`. Они запускаются независимо; Coordinator не создаёт Librarian и Reader через `fork()` или `exec()`.

Параметр `--session NAME` определяет общий префикс имён shared memory и именованных семафоров. Coordinator создаёт объекты, остальные программы открывают их по имени. Reader дополнительно получает индекс через `--reader INDEX`.

Участники регистрируются под блокировкой `state` и увеличивают семафор `ready`. Coordinator ждёт одного Librarian и всех Reader из config. Повторное подключение той же роли или индекса отклоняется. Модельный день сохраняет прежние фазы: возвраты библиотекаря, затем посещения читателей с подтверждением завершения каждой фазы.

При завершении Coordinator устанавливает `finished`, запрещает новые подключения и будит участников. Каждый зарегистрированный участник освобождает свои ресурсы и подтверждает выход через `exited`. Coordinator ждёт подтверждений и удаляет IPC. `waitpid()` для Librarian и Reader не используется, поскольку они не являются его дочерними процессами. Прямой SIGINT/SIGTERM участнику также прерывает его ожидание; Coordinator замечает досрочный выход и завершает сессию.

## 7. Реализация выше 8 баллов

Программы `library_10_coordinator`, `library_10_librarian` и `library_10_reader` запускаются независимо, без создания участников через `fork()` или `exec()`. POSIX shared memory не используется: книги, читатели, заявки, резервы и статистика находятся только у Coordinator. Централизованное владение состоянием исключает конкурентное изменение книг, заявок и резервов несколькими процессами, поэтому mutex для предметных данных не нужен.

Выбраны POSIX message queues: они сохраняют границы фиксированных сообщений и позволяют независимым программам открывать каналы по имени `--session`. Общая очередь `requests` принимает команды; очереди `librarian` и `reader_<index>` доставляют ответы конкретным участникам. Небольшая очередь `registration` и семафор `register` последовательно обслуживают подключения, чтобы отказ дубликату не мог получить уже работающий Reader.

Сообщение содержит версию протокола, тип, индекс Reader, день, идентификатор книги и результат. При регистрации передаётся также неизменяемый план Reader: имя, расписание, исходные желания и `request_rule`. Указатели, адреса памяти и файловые дескрипторы не передаются. Некорректные сообщения, дубликаты и неверные пользовательские параметры обрабатываются обычными проверками ошибок.

Семафор `ready` подтверждает подключение каждого участника, а `librarian_start` и `reader_<index>_start` задают начало фаз. Librarian получает день, отправляет `PROCESS_RETURNS` и после ответа сообщает `PHASE_DONE`. Reader сам проверяет расписание, начинает посещение, запрашивает свои резервы, проверяет доступность желаний и принимает решение для `always_wait`. Затем он отправляет отдельные попытки выдачи и при необходимости команды создания заявок. Coordinator применяет общие предметные функции и отвечает на каждую команду.

Посещения обслуживаются последовательно от `BEGIN_VISIT` до `PHASE_DONE`, сохраняя прежнюю критическую секцию целого посещения. Это не позволяет другому Reader изменить доступность книги между проверкой всего списка желаний и решением `always_wait`. Между днями допускается только демонстрационная задержка `--delay-ms N`, по умолчанию `0`; `--print-ipc` выводит имена созданных объектов.

При остановке Coordinator посылает `SHUTDOWN`, будит ожидающих участников и принимает `EXITED`. После подтверждений он выполняет `mq_close`/`mq_unlink` и `sem_close`/`sem_unlink`, затем выводит итог. `waitpid()` не используется: участники не являются его детьми. Ожидания сообщений и завершения ограничены по времени; неожиданный выход участника прекращает моделирование с ошибкой. Только Coordinator пишет предметный журнал `library.log` через `open`, `write`, `close` в режиме добавления, поэтому параллельные сессии не перезаписывают сообщения друг друга.

## 8. Завершение

В версиях 4-5 и 6 после последнего дня родитель устанавливает общий признак завершения и будит процессы, которые могут ожидать на семафорах. Дочерние процессы проверяют этот признак и выходят, после чего родитель собирает их через `waitpid()`.

SIGINT (`Ctrl+C`) и SIGTERM обрабатываются через `sigaction`. Обработчик только устанавливает флаг `volatile sig_atomic_t stop_requested`. Вывод, ожидание процессов и освобождение ресурсов выполняются обычным кодом программы.

В версии 4-5 при завершении уничтожаются неименованные семафоры и shared memory. В версии 6 закрываются и удаляются именованные семафоры, после чего также удаляется shared memory.

В версии 7-8 завершение независимых участников подтверждается через семафор `exited`, в финальной версии - сообщением `EXITED`. При частичном создании ресурсов освобождаются только успешно созданные объекты.

## 9. Сборка и запуск

Нужны Linux, CMake и компилятор C11 с поддержкой POSIX shared memory, message queues и семафоров.

Сборка:

```bash
cmake -S . -B build
cmake --build build
```

Версия на 4-5 баллов:

```bash
./run4_5.sh
```

Версия на 6 баллов:

```bash
./run6.sh
```

Версия на 7-8 баллов:

```bash
./run7_8.sh -c config.txt
```

Для ручного запуска выполните команды в отдельных терминалах из каталога проекта. После запуска Coordinator дождитесь сообщения о готовности сессии:

```bash
./build/library_7_8_coordinator --session demo -c config.txt
./build/library_7_8_librarian --session demo
./build/library_7_8_reader --session demo --reader 0
./build/library_7_8_reader --session demo --reader 1
./build/library_7_8_reader --session demo --reader 2
```

Финальная версия запускается через `./run10.sh -c config.txt`. Для ручного запуска замените в приведённых командах `library_7_8_` на `library_10_`. Coordinator также принимает `--delay-ms 200` для демонстрации и `--print-ipc` для вывода имён IPC.

Количество Reader определяется config; индексы начинаются с нуля. Для завершения сессии отправьте SIGINT/SIGTERM Coordinator.

Скрипты по умолчанию загружают `config.txt` из корня проекта. При прямом запуске `./build/library_4_5` или `./build/library_6` без `-c` используются встроенные данные.

Можно передавать те же параметры, что и в предыдущем ИДЗ:

```bash
./run4_5.sh -c config.txt -d 20 -r 5
./run6.sh -c config.txt -d 20 -r 5
```

Опции: `-d / --days` - количество дней, `-r / --reading-days` - срок чтения, `-c / --config` - файл конфигурации, `-h / --help` - справка. Значения CLI имеют приоритет над config.

## 10. Дополнительные возможности

- **Комментарии и Doxygen.** Логические блоки поясняются обычными комментариями, публичные структуры и функции описаны Doxygen-комментариями.
- **clang-format.** Исходные `.c` и `.h` приводятся к единому стилю через `.clang-format`.
- **SOFT_ASSERT.** Внутренние контракты и инварианты проверяются отдельно от пользовательских ошибок.
- **Работа с файловыми дескрипторами.** Логирование использует `open`, `write`, `close`.
- **Логирование.** Основные события и итоговая статистика сохраняются в `library.log`.
- **Статистика.** В конце выводятся количество посещений, выдач, возвратов, созданных и выполненных заявок, уведомлений.
- **Config и CLI.** Параметры модели можно изменять через config-файл и аргументы командной строки.
- **Обработка сигналов.** SIGINT и SIGTERM приводят к корректному завершению участников и освобождению IPC-ресурсов.
- **Тестовые сценарии.** Для каждой реализации предусмотрен отдельный интеграционный скрипт.

## 11. Тесты и результаты

Проект собирается через CMake с флагами `-Wall -Wextra -Wpedantic`.

Используются:

```bash
./test.sh
./test4_5.sh
./test6.sh
./test7_8.sh
./test10.sh
```

`test.sh` проверяет сохранённую pthread-версию ИДЗ №2, `test4_5.sh` - процессную реализацию с неименованными семафорами, `test6.sh` - вариант с именованными семафорами. `test7_8.sh` проверяет независимые программы, регистрацию, отклонение дубликатов и завершение с удалением IPC. `test10.sh` дополнительно проверяет очереди сообщений, две одновременные сессии, локальные сигналы участникам, диагностику IPC и совпадение статистики с прежними версиями.

Проверяются обычный сценарий, граничные случаи, FIFO/LIFO, `always_wait`, `on_unavailable`, параметры CLI, максимальное количество читателей, обычное завершение и остановка по сигналам.

Проверки используют Bash и `grep`, каждый запуск ограничен через `timeout`. Порядок независимых сообщений процессов не фиксируется. Для процессных вариантов также проверяется корректное завершение дочерних процессов и удаление IPC-ресурсов.

Результаты выполненного прогона:

| Скрипт | Результат |
| --- | --- |
| `./test.sh` | `Tests passed: 10/10` |
| `./test4_5.sh` | `Tests passed: 16/16` |
| `./test6.sh` | `Tests passed: 16/16` |
| `./test7_8.sh` | `Tests passed: 19/19` |

В исходном `normal_config.txt` два читателя создают заявки в один день. Их порядок не фиксирован, поэтому число выдач и возвратов может законно различаться между запусками. Для точного сравнения всех шести счётчиков во всех пяти версиях тест создаёт обычный сценарий с разными днями подачи заявок; исходный config остаётся отдельным тестом. На таком же сценарии сравниваются задержка по умолчанию и `--delay-ms 0`.

Проверка процессов через `ps` подтверждает независимый запуск и `NLWP = 1`. Очереди проверяются через `mq_open`/`mq_getattr`, семафоры - через `/dev/shm`; после обычного завершения и сигналов имена удаляются. В среде проверки `/dev/mqueue` не смонтирован, поэтому наличие и отсутствие очередей проверяется через API, а их имена показывает `--print-ipc`. На системе со смонтированным mqueuefs доступны также `ls /dev/mqueue` и `ls /dev/shm`.
