## 2. Условие задачи и модель

В сельской библиотеке каждая книга есть в одном экземпляре. Читатели приходят по расписанию, выбирают от одной до трёх книг и возвращают полученные книги через заданное число дней. На недоступные книги создаются заявки. После возврата библиотекарь уведомляет ожидающих и резервирует книгу одному из них.

Из предыдущих ИДЗ сохранены предметные структуры, формат config, FIFO/LIFO, правила формирования заявок и статистика. В ИДЗ №4 независимые программы взаимодействуют по TCP вместо локального IPC.

Входные данные задают книги, читателей, посещения, желаемые книги, срок чтения, `strategy` и `request_rule`. При `on_unavailable` доступные книги выдаются сразу, на недоступные создаются заявки. При `always_wait` наличие недоступной желаемой книги откладывает обычную выдачу остальных свободных книг. Собственные резервы обрабатываются первыми; получить резерв можно при посещении позже дня резервирования.

Основные инварианты:

- У книги не более одного владельца; выданная книга отсутствует в доступном фонде.
- Повторная выдача той же книги читателю до возврата невозможна.
- Возвращённая книга свободна либо зарезервирована одному ожидающему; уведомление нескольких читателей не означает выдачу каждому.
- Закрытая заявка не обслуживается повторно, активная заявка одного читателя на одну книгу не дублируется.

Модель заканчивается по истечении заданного периода, по умолчанию 13 дней. Оставшиеся заявки и резервы выводятся вместе со статистикой, бесконечного ожидания их выполнения нет. Стандартный `config.txt` содержит две книги, трёх читателей и срок чтения 3 дня. "Выполненная заявка" в статистике означает её выбор и закрытие при резервировании, а не обязательное получение книги в этот день.

## 3. Архитектура

Реализованы четыре независимых консольных приложения на C11 для Linux:

| Программа | Назначение |
| --- | --- |
| `library_server` | Хранит состояние библиотеки, принимает соединения и управляет модельными днями |
| `library_librarian_client` | Инициирует обработку возвратов и подтверждает завершение своей фазы |
| `library_reader_client` | Представляет одного Reader, получает личное расписание и инициирует посещения |
| `library_observer_client` | Показывает общий поток событий, не изменяя модель |

Каждый Reader имеет собственное расписание и запускается отдельным процессом; Librarian также является самостоятельным процессом. `Book` и `Request` остаются данными без самостоятельного поведения. Сервер - единственный владелец изменяемой `Simulation`. Клиенты не читают серверный config и не хранят копию модели.

В начале дня Librarian инициирует возвраты. После завершения этой фазы сервер разрешает посещения Reader и ждёт подтверждений всех читателей. Возвраты всегда предшествуют посещениям; независимые посещения обрабатываются по готовности сообщений. Предметные действия выполняются последовательно, поэтому проверка доступности книги и изменение владельца не конкурируют между собой.

Один цикл `poll()` обслуживает неблокирующие серверные сокеты, накапливает частичные сообщения и отправляет ответы. Отдельные потоки для соединений не создаются. TCP-сборка использует `LIBRARY_TCP`, исключающий прежние pthread и семафоры из модели. Исходники, скрипты и CMake targets ИДЗ3 сохранены.

### Реализация на 4-5 баллов

`library_server`, `library_librarian_client` и отдельные `library_reader_client` обмениваются командами и результатами по TCP. Server хранит общее состояние `Simulation`, а клиенты инициируют действия своих ролей. Каждая программа получает и отображает свою часть информации. IP и порт задаются через CLI, Reader дополнительно передаёт свой индекс.

### Реализация на 6-7 баллов

Отдельный `library_observer_client` получает `NET_OBSERVER_EVENT`, объединяющие границы дней, фазы участников и предметные события в одну картину модели. Observer не изменяет `Simulation` и не участвует в барьерах рабочих ролей.

### Реализация на 8 баллов

Одновременно подключаются несколько Observer; сервер ставит события в очередь отправки каждому активному наблюдателю. Разрыв одного соединения не влияет на модель и остальных участников. Новый Observer может подключиться во время работы и получает последующие события. Медленный Observer обслуживается независимо и при переполнении своего выходного буфера отключается, не блокируя Server.

### Реализация бонусов выше 8 баллов

Reader и Librarian могут отключаться и подключаться снова, пока `Simulation` остаётся на Server. `WorkerProgress` хранит `day`, `operation_applied` и `phase_done`, а `NET_WORKER_SYNC` синхронизирует восстановленного клиента. Уже применённая операция повторно не выполняется.

При SIGINT/SIGTERM обработчик устанавливает флаг, а серверный цикл рассылает `NET_FINISHED`; исправные клиенты завершаются штатно. Ожидание отправки ограничено по времени. Техническая механика сохранения прогресса и завершения соединений подробнее описана в разделе 6.

## 5. Сетевой протокол

Сообщение занимает **24 байта** и состоит из шести 32-битных полей:

| Поле | Назначение |
| --- | --- |
| `type` | Тип сообщения |
| `reader_index` | Индекс Reader либо обозначение служебной роли |
| `day` | Модельный день |
| `book_id` | Идентификатор книги |
| `code` | Код события, флаги синхронизации или причина завершения |
| `value` | Дополнительное значение, определяемое типом сообщения |

В `src/protocol.c` применяется явная сериализация через `htonl()/ntohl()`. Сырая C-структура, padding и указатели по сети не передаются. Reader задаётся индексом 0..N-1 в config, который не обязательно совпадает с предметным `Reader.id`. Служебные значения: Librarian - `-1`, незарегистрированное соединение - `-2`, Observer - `-3`.

После регистрации Reader получает личное расписание. Команды запускают фазы Librarian/Reader, ответы передают события и подтверждения. `NET_OBSERVER_EVENT` передаёт общий поток, `NET_WORKER_SYNC` - сохранённый прогресс, `NET_FINISHED` - штатное окончание или остановку сервера. Частичные чтения/записи и `EINTR` обрабатываются; сервер не использует блокирующее чтение внутри своего цикла.

## 6. Reconnect и завершение

Физическое TCP-соединение может исчезнуть, а логическое состояние Reader/Librarian остаётся на сервере. `WorkerProgress` хранит день, признак уже применённой операции `operation_applied` и признак завершённой фазы `phase_done`. После повторного запуска клиент получает `NET_WORKER_SYNC`: уже применённое предметное действие не повторяется. Второе активное соединение той же рабочей роли отклоняется. Если для продолжения нужна отсутствующая роль, модель ждёт её восстановления, а сервер продолжает обслуживать сеть.

Reconnect выполняется новым запуском программы с прежней ролью или индексом Reader. Автоматическое переподключение и восстановление после перезапуска самого сервера не реализованы. Observer может подключаться в любой момент и видит события с момента подключения; история не воспроизводится.

SIGINT/SIGTERM обрабатываются через `sigaction`; handler только устанавливает флаг. Обычный серверный цикл рассылает `NET_FINISHED` и завершает соединения. Исправные подключённые clients и server выходят с кодом 0, неожиданный EOF остаётся ошибкой. Ожидание завершения ограничено примерно двумя секундами, поэтому зависший клиент не удерживает сервер бесконечно.

## 7. Сборка и запуск

Команды выполняются из каталога `hw4`:

```bash
cmake -S . -B build
cmake --build build
```

Собираются четыре сетевых приложения и сохранённые targets ИДЗ3. Для локального запуска каждая следующая команда выполняется в отдельном терминале:

```bash
./build/library_server --host 127.0.0.1 --port 5050 -c config.txt
./build/library_observer_client --host 127.0.0.1 --port 5050
./build/library_librarian_client --host 127.0.0.1 --port 5050
./build/library_reader_client --host 127.0.0.1 --port 5050 --reader 0
./build/library_reader_client --host 127.0.0.1 --port 5050 --reader 1
./build/library_reader_client --host 127.0.0.1 --port 5050 --reader 2
```

Observer необязателен; для полного потока его подключают до последнего обязательного участника. Вывод участников можно смотреть в терминалах либо перенаправлять в отдельные файлы.

Для уровня 8 можно одновременно запустить несколько Observer в разных терминалах:

```bash
./build/library_observer_client --host 127.0.0.1 --port 5050
./build/library_observer_client --host 127.0.0.1 --port 5050
```

Все подключённые Observer получают общий поток событий. Отключение одного Observer не влияет на работу модели и остальных наблюдателей; новый Observer можно подключить во время выполнения программы.

Все программы требуют числовой IPv4 и порт 1..65535; `-h/--help` доступен без параметров подключения. Сервер поддерживает `-c/--config FILE`, `-d/--days N`, `-r/--reading-days N`. CLI имеет приоритет над config, без `-c` используются встроенные данные. Например:

```bash
./build/library_server --host 127.0.0.1 --port 5050 -c config.txt -d 20 -r 5
```

Базовый запуск можно выполнить скриптом:

```bash
./scripts/run4_5_tcp.sh
./scripts/run4_5_tcp.sh -c tests/configs/one_reader_one_book.txt --port 5051
```

Он запускает server, Librarian и нужное число Reader без Observer, сохраняет отдельные журналы в `build/tcp-run.XXXXXX/` и очищает собственные процессы по PID.

### Несколько компьютеров

Например, на сервере с адресом `192.168.1.10`:

```bash
./build/library_server --host 0.0.0.0 --port 5050 -c config.txt
```

На других Linux-компьютерах:

```bash
./build/library_observer_client --host 192.168.1.10 --port 5050
./build/library_librarian_client --host 192.168.1.10 --port 5050
./build/library_reader_client --host 192.168.1.10 --port 5050 --reader 0
```

Остальные Reader запускаются аналогично. Нужны совместимые бинарники и доступный TCP-порт; общая файловая система не требуется. `0.0.0.0` используется для bind сервера, клиенту нужен реальный IPv4.
